# اجرای مسیر توسعهٔ تعمیران با Ruflo و Codex

مسیر پیاده‌شده:

**تحلیل → طراحی → پیاده‌سازی → تست → بازبینی**

تعریف قابل نسخه‌بندی در [tamiran.json](../../workflows/tamiran.json) و فرمان‌ها در [tamiran_flow.py](../../scripts/tamiran_flow.py) قرار دارند. هر اجرا پنج وظیفهٔ واقعی در Ruflo دارد و شناسه، وضعیت، خروجی و هش شواهد هر مرحله را نگه می‌دارد. مراحل به ترتیب طی می‌شوند؛ مرحلهٔ تست بدون آزمون واقعیِ موفق تکمیل نمی‌شود.

این اتصال از API وظایف Ruflo استفاده می‌کند. به‌دلیل [محدودیت‌های تأییدشدهٔ workflow CLI](WORKFLOW-REVIEW-FA.md)، اجرای فایل از `workflow run --file` مبنای این مسیر نیست. اجرای کار با Codex انجام می‌شود و مدل یا سطح مجوزهای آن تغییر نمی‌کند. در حالت هدایت توسط نشست فعلی، همین نشست نقش‌ها را انجام می‌دهد؛ در حالت `run`، فرمان `codex exec` برای مراحل به ترتیب اجرا می‌شود.

## پیش‌نیازها

- Python 3.11 یا جدیدتر در Linux یا macOS؛ برای Windows از WSL استفاده کنید.
- Ruflo نسخهٔ آزمایش‌شدهٔ `3.71.4` و Node.js 20+.
- برای اجرای خودکار، Codex CLI نصب‌شده و حساب متصل (`codex login status`).
- Git و پیش‌نیازهای پروفایل انتخابی.

از ریشهٔ مخزن:

```sh
python3 scripts/tamiran_flow.py plan
python3 scripts/tamiran_flow.py doctor
```

`doctor` وضعیت هر پیش‌نیاز را جدا نشان می‌دهد؛ موجود بودن Ruflo، به معنی آماده‌بودن همهٔ پروفایل‌ها نیست.

| پروفایل | کاربرد و بررسی‌های الزامی |
|---|---|
| `tooling` | تغییر ابزار و مستندات؛ آزمون کنترل جریان، foundation و ۶۷ هش مرجع. تغییر منطق برنامه در این پروفایل پذیرفته نمی‌شود. |
| `frontend-static` | TypeScript، build و حفظ مرجع. ابتدا در `hosting/frontend` با lockfile خود پروژه `npm ci --ignore-scripts` اجرا شود. کار تعاملی به شواهد مرورگر هم نیاز دارد و بازبینی می‌تواند تا ارائهٔ آن متوقف بماند. |
| `backend-local` | نحو PHP و تست اصلی API در نصب PHP/MariaDB آزمایشیِ از قبل آماده‌شده روی loopback. به PHP CLI و متغیر امن `TAMIRAN_SMOKE_ADMIN_PASSWORD` برای مدیر مصنوعی `09120000000` نیاز دارد. |

پروفایل backend از `http://127.0.0.1:8085` استفاده می‌کند. برای پورت محلی دیگر، `TAMIRAN_TEST_URL` قابل تنظیم است؛ میزبان عمومی، نشانی دارای credential یا query پذیرفته نمی‌شود. این پروفایل دیتابیس یا سرور آزمایشی را ایجاد نمی‌کند و برای staging، هاست مشتری یا دادهٔ واقعی نیست.

## هدایت مراحل در همین نشست کدکس

شروع فقط وظایف را ثبت می‌کند و مدل دیگری اجرا نمی‌کند:

```sh
python3 scripts/tamiran_flow.py start --task "شرح دقیق تغییر موردنیاز" --profile tooling
```

خروجی، شناسهٔ `run` و پنج شناسهٔ Ruflo را می‌دهد. به‌جای `RUN_ID` همان شناسه را قرار دهید:

```sh
python3 scripts/tamiran_flow.py next --run RUN_ID
python3 scripts/tamiran_flow.py status --run RUN_ID
```

`next` دستور مرحله، نقش متناسب ECC، نتایج قبلی و شواهد آزمون را نشان می‌دهد. پس از انجام واقعی کار، خروجی JSON مطابق [result.schema.json](../../workflows/result.schema.json) تهیه کنید:

```json
{
  "outcome": "pass",
  "summary": "شرح کار واقعاً انجام‌شده و نتیجهٔ آن",
  "findings": [],
  "tests": ["دستور اجراشده و نتیجه، یا توضیح آزمون اجرا‌نشده"],
  "risks": []
}
```

ثبت خروجی مرحلهٔ جاری:

```sh
python3 scripts/tamiran_flow.py record --run RUN_ID --stage research --result /path/to/result.json
```

شناسهٔ مرحله‌ها `research`، `design`، `implement`، `test` و `review` است. تلاش برای پرش از مراحل، تکمیل دوباره، تغییر سورس در تحلیل/طراحی/بازبینی یا تغییر شواهد تکمیل‌شده رد می‌شود. تغییر سورس فقط در محدودهٔ پروفایل پذیرفته می‌شود؛ مرجع منجمد مستقل از پروفایل کنترل می‌شود.

در مرحلهٔ تست، ابتدا فرمان واقعی زیر را اجرا کنید و پس از موفقیت، خروجی مرحله را ثبت کنید:

```sh
python3 scripts/tamiran_flow.py check --run RUN_ID
python3 scripts/tamiran_flow.py record --run RUN_ID --stage test --result /path/to/test-result.json
```

شکست هر فرمان، نبود ابزار لازم، تغییر سورس پس از آزمون یا دست‌کاری log اجازهٔ تکمیل مرحلهٔ تست را نمی‌دهد. `outcome: blocked` نیز مسیر را متوقف می‌کند. موفقیت صرفاً ادعای خلاصهٔ مدل نیست؛ کنترل‌کننده کد خروج فرمان‌ها، وضعیت Ruflo و هش شواهد را بررسی می‌کند. با این حال، کیفیت معنایی تحقیق و بازبینی همچنان مسئولیت عامل انجام‌دهنده است.

## اجرای خودکار با Codex CLI

این فرمان اجرای واقعی مراحل با Codex را آغاز می‌کند:

```sh
python3 scripts/tamiran_flow.py run --task "شرح دقیق تغییر ابزار" --profile tooling
```

مدل، sandbox و تنظیمات مجوز از Codex به ارث می‌رسند. نقش‌ها اجازهٔ ساخت ایجنت دیگر، اجرای workflow بازگشتی، انتشار سایت یا ارسال واقعی ندارند. خروجی ساختاری هر مرحله ثبت می‌شود و فرمان‌های آزمون را خود کنترل‌کننده اجرا می‌کند. اگر مرحلهٔ فقط‌خواندنی سورس را تغییر دهد، خروج غیرموفق رخ دهد یا مهلت تمام شود، اجرا متوقف و شواهد حفظ می‌شوند؛ تغییرات کاربر خودکار reset نمی‌شوند.

ادامه پس از رسیدگی به دلیل توقف:

```sh
python3 scripts/tamiran_flow.py run --run RUN_ID --retry
```

مراحل تکمیل‌شده تکرار نمی‌شوند؛ خروجی تلاش‌های قبلی باقی می‌ماند. برای تغییر خود تعریف مسیر یا اصلاح کد پس از بازبینی نهاییِ مسدودشده، اجرای تازه‌ای شروع کنید تا ترتیب پیاده‌سازی و تست دوباره طی شود. تغییر مدل/سطح دسترسی یا نصب پیش‌نیازها خودکار انجام نمی‌شود.

## وضعیت و نگهداری

```sh
python3 scripts/tamiran_flow.py status --run RUN_ID
ruflo task list
```

فرمان اول مراحل و شواهد همین مسیر را نشان می‌دهد؛ فرمان دوم وظایف پایدار Ruflo را. این مسیر در فهرست native `ruflo workflow list` ثبت نمی‌شود، زیرا هماهنگی آن با API وظایف و اجرای آن با Codex است.

داده‌های اجرا در `.ruflo/tamiran/` و `.claude-flow/` هستند و در Git ثبت نمی‌شوند. وضعیت تاریخی `completed` مربوط به زمان اجرای ثبت‌شده است؛ `status` جداگانه نشان می‌دهد آیا worktree هنوز با آخرین شواهد تکمیل‌شده یکسان است. برای تغییرات جدید اجرای تازه بسازید. نشست اصلی پس از بررسی شواهد، مطابق خواستهٔ مالک پروژه commit/push می‌کند؛ خود runner کد را منتشر یا سایت را deploy نمی‌کند.

## شواهد این پیاده‌سازی

خلاصهٔ قابل پردازش بررسی‌ها در [WORKFLOW-VERIFICATION.json](WORKFLOW-VERIFICATION.json) ثبت شده است.

```sh
TAMIRAN_RUFLO_INTEGRATION=1 python3 -m unittest discover -s tests/ruflo -p 'test_*.py' -v
```

۳۱ آزمون رفتاری و اتصال واقعی به Ruflo موفق شدند. آزمون اتصال، پنج وظیفه را در پوشهٔ موقت ثبت می‌کند، سرور MCP را دوباره باز می‌کند و تکمیل همراه شواهد را از Ruflo می‌خواند. آزمون اجرای `codex exec` از برنامهٔ محلیِ صریحاً آزمایشی استفاده می‌کند؛ مدل زنده اجرا نشده است. پوشش خطی کنترل‌کننده با `trace` استاندارد Python برابر ۸۳٪ اندازه‌گیری شد؛ این پوشش کد برنامهٔ تعمیران یا branch coverage نیست.

در محیط این پیاده‌سازی، پیش‌نیازهای `tooling` موجود بودند؛ dependencyهای frontend در checkout جدید و PHP CLI/مدیر مصنوعی backend آماده نبودند و به‌عنوان آماده یا پاس گزارش نشدند. foundation و ۶۷ هش مرجع نیز تأیید شدند.
