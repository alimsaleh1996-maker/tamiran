# بررسی جریان کاری Ruflo برای تعمیران

بررسی ۵ نوامبر ۲۰۲۶، روی **Ruflo 3.71.4**. راهنمای CLI با رفتار واقعی dry-run و اعتبارسنجی ساختار مقایسه شد؛ هیچ ایجنت مدل، گردش کاری عملیاتی، job زمان‌بندی یا استقرار اجرا نشد.

## وضعیت فعلی

- CLI و سرور MCP در تنظیمات محلی Codex نصب‌اند.
- `ruflo init check` برای پوشهٔ تعمیران، مقداردهی‌نشدن پروژه را گزارش داد.
- `ruflo workflow list` هیچ workflow ثبت‌شده‌ای نشان نداد.
- `workflow status` به شناسه نیاز دارد؛ نصب ابزار به معنی وجود گردش کاری آمادهٔ اجرا نیست.

## نتیجهٔ آزمون‌ها

| بررسی | نتیجهٔ مشاهده‌شده |
|---|---|
| قالب `development` از CLI با `--dry-run` | فقط یک مرحله با نام `Execute` و صفر ایجنت |
| قالب `feature` از CLI | رد شد؛ نام در فهرست مجاز CLI نیست |
| قالب `feature` از MCP، با `options.dryRun: true` | پنج مرحلهٔ Research، Design، Implement، Test و Review؛ صفر ایجنت |
| فایل JSON آزمایشی با سه مرحلهٔ `wait`، اعتبارسنجی strict | معتبر؛ سه مرحله و بدون نیاز به ایجنت |
| JSON بدون آرایهٔ مراحل | نامعتبر، exit code برابر 1 |
| فایل YAML با ساختار مراحل | نامعتبر؛ ابزار صریحاً هشدار می‌دهد که اعتبارسنجی schema برای YAML پیاده نشده است |
| همان فایل JSON سه‌مرحله‌ای با `workflow run --file ... --dry-run` | فقط یک مرحلهٔ `Execute`؛ مراحل فایل در این مسیر مصرف نشدند |

بنابراین در نسخهٔ بررسی‌شده، نام قالب‌های CLI با شاخه‌های قالب در handler مربوط به MCP هم‌خوان نیست. `workflow_run` مسیر فایل را کنترل می‌کند، اما تعریف مراحل فایل را نمی‌خواند؛ dry-run موفق برای این مسیر، تأیید اجرای فایل دلخواه نیست. اعتبارسنجی JSON نیز یک بررسی ساختاری است و به‌تنهایی اجرای مراحل یا رفتار تجاری را ثابت نمی‌کند.

در پیاده‌سازی `@claude-flow/cli` نسخهٔ 3.71.4، فایل `dist/src/commands/workflow.js` گزینه‌های CLI و فایل `dist/src/mcp-tools/workflow-tools.js` رفتار MCP را تعیین می‌کنند. نام‌های `feature`، `bugfix`، `refactor` و `security` در handler وجود دارند؛ نام‌های مجاز CLI شامل `development`، `research`، `testing`، `security-audit`، `code-review`، `refactoring`، `sparc` و `custom` هستند. موارد مقایسه‌شده در جدول، واقعاً اجرا و خروجی‌شان ثبت شده‌اند.

## دستور آزمایشی تأییدشده

این فرمان، برنامهٔ پنج‌مرحله‌ای را از MCP دریافت می‌کند و ایجنتی اجرا نمی‌کند:

```sh
ruflo mcp exec -t workflow_run -p '{"template":"feature","task":"Review Tamiran workflow","options":{"dryRun":true}}'
```

در اجرای آزمایشی نتیجه `validated`، تعداد مراحل ۵ و `agentsSpawned` برابر صفر بود. `estimatedDuration` نیز `unknown` است؛ زمان تقریبی را نباید به‌عنوان اجرای اندازه‌گیری‌شده گزارش کرد.

بدون dry-run، `workflow_run` فقط workflow را در حالت `ready` ثبت می‌کند. شروع اجرای واقعی وظیفهٔ `workflow_execute` است و مراحل task به `config.agentId` یا `options.defaultAgentId` متصل می‌شوند. در این بررسی workflow واقعی ساخته یا اجرا نشده است.

## ترتیب مناسب برای کار روی تعمیران

1. مشخص‌کردن مسئله و خواندن نقشهٔ Graphify با توجه به تفاوت نسخهٔ PHP، Worker و مرجع منجمد.
2. برنامه‌ریزی تغییر با نقش ECC متناسب با مسئله و قراردادهای فعلی پروژه.
3. اعمال تغییر محدود با حفظ مجوزهای سروری، نسخه‌ها و تراکنش‌های تجاری.
4. اجرای بررسی‌های مرتبط: TypeScript و build برای رابط، PHP/API/SQL برای بک‌اند و مرورگر برای رفتار تعاملی.
5. بازبینی نتیجه و شواهد؛ ساخت و آزمون ZIP در تغییرهایی که به نسخهٔ نصب‌شدنی می‌رسند.
6. commit و push در GitHub و تأیید SHA سرور، مطابق خواستهٔ مالک پروژه.

Ruflo می‌تواند ثبت، هماهنگی و وضعیت مراحل را نگه دارد؛ اتصال واقعی مراحل به ایجنت‌ها و نتیجهٔ آزمون‌ها باید جداگانه اثبات شود. با محدودیت‌های فعلی CLI، `workflow run --file` یا عبارت `validated` را مبنای تکمیل خودکار این زنجیره قرار ندهید.

برخی فرمان‌های بررسی، فایل‌های policy اجرایی در `.claude-flow` ایجاد کردند. وضعیت تولیدشده در آزمایش به پوشهٔ scratch منتقل شد و مسیرهای `.claude-flow/` و `.ruflo/` از Git کنار گذاشته شدند. کد برنامه و تنظیمات نقش‌ها، مدل و مجوزهای Codex تغییر نکردند.

[شواهد ماشین‌خوان بررسی](workflow-review.json). آزمایش‌ها در پوشهٔ ایزوله با داده‌های `TEST` و بدون تماس با دیتابیس، مشتری، درگاه یا پیامک انجام شدند. این گزارش، مرور نصب و جریان کاری ابزار است؛ بازبینی تازهٔ منطق گردش تعمیر یا تست اجرای API تعمیران نیست.
