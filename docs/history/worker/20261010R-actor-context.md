# اجرای 20261010R — هویت عملیاتی و انتخاب شعبه

نسخه مبنا: `c495bb5f0a6e76a3aa7cc3d109a097f42aad1a7c`. دامنه این اجرا فقط قرارداد خواندنی `GET /api/auth.php` برای تبدیل هویت احرازشده Sites به actor و context معتبر D1 بود. رابط، ۲۰ منو، schema و migrationها تغییر نکردند. استیجینگ، داده مشتری واقعی، پیامک و پرداخت واقعی استفاده نشدند. Candidate هنوز جایگزین انتشار static فعال نیست و آمادگی پایلوت تأیید نشده است.

## علت و تغییر محدود

ممیزی قبلی نشان داد رابط برای bootstrap به `GET /api/auth.php` وابسته است، اما dispatcher جدید این مسیر را منتقل نکرده بود. در نتیجه هویت Sites هنوز به نقش، تعمیرگاه و شعبه authoritative دیتابیس تبدیل نمی‌شد و اتصال ایمن adapter رابط ممکن نبود.

پیاده‌سازی این مرحله:

- شناسه کاربر احرازشده Sites فقط کلید اتصال به `account_user_id` است؛ نام، نقش، تعمیرگاه یا شعبه ارسالی از رابط منبع اعتماد نیست.
- مدیر مرکزی فعال و هر شش نقش عملیاتی شعبه از user/binding/membership/branch فعلی D1 حل می‌شوند و نام نمایشی، role شعبه، permissions و پروفایل مجاز تعمیرگاه برمی‌گردند.
- هویت دارای بیش از یک شعبه یا تعمیرگاه actor پیش‌فرض نمی‌گیرد؛ فقط contextهای مجاز و کمینه را دریافت می‌کند و باید `branchId` مجاز را صریح انتخاب کند.
- حساب ناشناس یا unbound، کاربر/عضویت/شعبه غیرفعال، تعمیرگاه suspended، شعبه بیگانه و پارامتر جعلی یا تکراری fail-closed هستند. مدیر مرکزی انتخاب شعبه نمی‌پذیرد.
- وضعیت `read_only` یا انقضای مجوز در پروفایل خواندنی دیده می‌شود تا رابط علت محدودیت را نشان دهد؛ این endpoint مجوز نوشتن اعطا نمی‌کند و مسیرهای نوشتنی موجود همچنان scope فعال خود را دوباره کنترل می‌کنند.
- JSON اختیاری permissions/modules/feature flags sanitize می‌شود؛ password hash، account binding، config خصوصی یا source در پاسخ نیست. چون احراز هویت را Sites انجام می‌دهد، وضعیت legacy password وارد قرارداد نشده است.
- `POST` و `DELETE` احراز هویت عمداً منتقل نشدند و پاسخ موفق ساختگی ندارند. سیاست original single-active-session/logout نیز در این مرحله پیاده‌سازی نشده است.

## Blast radius و محدودیت

- schema، migration، UI، منو و baseline frozen تغییر نکردند؛ endpoint فقط خواندنی است.
- adapter رابط هنوز context انتخاب‌شده را روی همه APIها و cache توکن CSRF شعبه اعمال نمی‌کند. نسخه‌های draft/terms/device/case نیز هنوز باید از پاسخ‌های واقعی به درخواست‌های پذیرش متصل شوند.
- قرارداد `POST/DELETE auth`، single-active-session و logout/revocation یک گام مستقل می‌خواهند. عملیات `read_only/expired` نیز نیازمند گام محدود سیاست دسترسی است؛ endpoint حاضر فقط وضعیت را نمایش می‌دهد.
- Worker/API و D1 میزبانی‌شده فعال یا آزموده نشدند. تست مرورگر، موبایل و چاپ نیز به‌علت نبود ابزار کنترل مرورگر اجرا نشد.
- POST رویداد/درخواست فعال‌سازی قابلیت، انبار simple/pro و چرخه کامل تکنسین تا تحویل هنوز fail-closed یا منتقل‌نشده‌اند.

نقطه ادامه: adapter رابط برای انتخاب شعبه و cache CSRF وابسته به همان شعبه، سپس اتصال `draftExpectedVersion`، نسخه/هش شرایط نمایش‌داده‌شده و نسخه‌های device/case. پس از آن سیاست نشست/logout و POST قابلیت‌ها باید در گام‌های تراکنشی و ممیزی‌شده جدا تکمیل شوند.
