# ادامه توسعه و تست خودکار تعمیران

## اختیار و مقصد

کاربر در ۱۸ مهر ۱۴۰۵ ادامه توسعه در پس‌زمینه، رفع ایراد و تست کل پروژه با مشخصات آزمایشی را تأیید کرده است. هدف آمادگی پایلوت جمعه ۲۴ مهر ۱۴۰۵ / ۱۶ اکتبر ۲۰۲۶ است، نه تضمین زمانی یا تضمین صفر باگ.

تنها پروژه مجاز: `appgprj_6abc1a7567b48191a56163caace8160f`، با حفظ دسترسی فعلی مالک-خصوصی. منبع پایدار، مخزن Git متعلق به همین Site است. از scratch قبلی، استیجینگ، cPanel، DirectAdmin یا دیتابیس واقعی استفاده نشود. هیچ درخواست شبکه، ورود یا استقرار روی استیجینگ انجام نشود. هیچ Site جدید یا دعوت مشتری/تکنسین واقعی ایجاد نشود.

## ابتدای هر اجرا

1. مهارت Sites و مراجع ضروری همان نوبت را کامل بخوان. `get_site` را برای همین شناسه بگیر؛ دسترسی/مالکیت و نسخه را بررسی کن. اگر مخاطب تغییر کرده یا نیاز به تأیید/اتصال وجود دارد، توقف و گزارش؛ با تغییر مخاطب محدودیت را دور نزن.
2. از `create_source_repository_write_credential` اعتبار تازه همین مخزن را بگیر. آن را فقط در حافظه نگه دار و از stdin به helper رسمی source بده؛ هیچ رمز/توکن در فایل، log، prompt یا command arguments نباشد.
3. در پوشه خالی، source helper را در حالت opening و بدون `archivePath` اجرا کن. از checkout_path و کل نتیجه opening استفاده کن. هیچ‌گاه به مسیر محلی این گفت‌وگو یا credential قبلی تکیه نکن.
4. `migration/README.md`، این راهنما و `migration/progress.json` را از آخرین HEAD بخوان. فایل‌های مرجع frozen و baseline-manifest را حفظ کن. اگر کار دستی هم‌زمان وجود دارد، آن را overwrite نکن. push باید معمولی باشد؛ conflict/non-fast-forward نیاز به تطبیق با نسخه تازه دارد، نه force/reset.
5. یک مرحله محدود از اولین کار آماده در progress را انتخاب کن. هدف هر نوبت یک تغییر کوچکِ قابل آزمون و checkpoint است، نه کار نامحدود و بی‌پایان.

## اجرا و آزمون

- UI واقعی و ۲۰ منو در `migration/worker/app/tamiran` هستند. ۳۸ API مرجع در `baseline/api` و قواعد اصلی در `baseline/private/v2-core.php` هستند. `dist/app.js` دموی قدیمی است و مبنای منطق محصول نیست.
- API، دیتابیس، مجوز، capability، پرداخت، انبار و رفتار انتقال را از سورس واقعی بررسی کن؛ شبیه‌ساز ساده یا پاسخ `ok:true` برای endpoint ناقص ننویس. اصلاح ایراد باید root cause، blast radius و regression test داشته باشد.
- قدم بعدی واقعی D1 schema/constraints و ذخیره‌سازی اتمیک است؛ `lib/workflow.ts` فقط برنامه‌ریز است. facts از DB معتبر خوانده شوند. version check، UPDATE شرطی، رویداد و audit و آثار مالی باید اتمیک باشند. تولید شماره قبض و retry نباید رکورد دوباره یا شماره تکراری بدهند.
- مهارت Storage: Drizzle schema، تولید migration رسمی، schema-only، حفظ migration اجراشده و seed آزمایشی جدا. حذف table/data، تغییر تاریخچه migration یا بازنویسی DB واقعی ممنوع است.
- هویت باید server-side و متعلق به Site/عضویت/شعبه باشد. role از query/DOM/انتخاب نمای نقش معتبر نیست. Site service credential هویت کاربر نمی‌دهد؛ برای تست نقش‌ها مجوز scoped واقعی و fixture آزمایشی طراحی و آزمون شود، نه impersonation عمومی یا bypass ورود.
- قبل از تغییر واحد پول و تاریخ، قرارداد موجود را بررسی کن. مبلغ باید integer باشد. تاریخ شمسی UI و UTC ذخیره‌سازی، مجوز حذف داده دستگاه و حدود تأیید هزینه حفظ شوند.
- همه fixtureها دارای شناسه `TEST-TAMIRAN-<run>-<scenario>` و نام «آزمایشی — …» باشند. اطلاعات مشتری واقعی، شماره مقصد واقعی، SMS واقعی، پرداخت واقعی و اسناد واقعی استفاده نشود. mock SMS فقط sink آزمایشی server-side باشد و نباید مسیر OTP/محدودیت تلاش را حذف کند.
- تست بخش تازه، رگرسیون بخش‌های وابسته، role-denial، cross-shop/branch، stale-version، double-click/retry، failure/rollback و راه اصلی موفق را اجرا کن. حداقل پایه‌های فعلی workflow/source-preservation/site-foundation برقرار بمانند.
- وضعیت `passed` فقط با نتیجه اجرای واقعی آزمون مجاز است. ساختن checklist، parse سورس، build، TypeScript و unit test به معنی browser/E2E/تست دیتابیس نیست. نوع، دستور، نسخه/commit، expected/actual و محدودیت را ثبت کن.
- نصب وابستگی فقط در صورت نبود یا تغییر inputs و با helper رسمی؛ هم‌زمان چند installer اجرا نشود. Candidate فعلی در زیرپوشه worker است؛ installer/build در همان checkout مربوط اجرا شود. بدون AGENTS/skill یا درخواست صریح، subagent نساز.
- managed Linux: اگر control-browser در دسترس نیست، browser QA را `blocked` ثبت کن؛ preview بداهه، مرورگر جایگزین یا نصب مرورگر برای دورزدن مهارت انجام نشود. آزمون چاپ/ریسپانسیو را بدون مشاهده واقعی پاس اعلام نکن.

## ذخیره، انتشار و بازیابی نوبت بعد

1. progress را با کاری که واقعاً انجام شد، موارد باقیمانده و evidenceهای غیرحساس به‌روز کن. در `docs/history/worker/` یک گزارش متنی با run ID، علت/دامنه تغییر، تست‌ها و قدم بعدی ثبت کن. اطلاعات شخصی و credential در گزارش نباشد.
2. تغییرات سالم با source helper رسمی commit/push/package و همان project_id منتشر شوند. دسترسی مالک-خصوصی حفظ شود؛ اگر tool approval یا permission شکست خورد، توقف و گزارش، نه bypass. از saved_version_id/deployment_id موجود برای ادامه استفاده کن، نسخه دوباره بی‌دلیل نساز.
3. فعلاً انتشار فعال static و دارای هشدار دموست. Candidate ناقص نباید به‌عنوان نرم‌افزار عملیاتی جایگزین شود. تا APIها و تراکنش‌های لازم و regressionهای مربوط پاس نشده‌اند، پیشرفت و وضعیت را منتشر کن، نه ادعای آماده‌بودن. هنگام انتقال نهایی طبق static-to-Worker راهنمای Sites عمل کن، همان مخزن/id/audience/bindings را حفظ کن و PHP/config خصوصی را در assets قرار نده.
4. success deployment فقط استقرار را اثبات می‌کند. آزمون API/DB با دسترسی unattended مجاز باید جدا اجرا و readback شود. اگر احراز هویت نقش یا مرورگر در دسترس نیست، آن تست blocked باقی می‌ماند؛ اجازه شروع داده واقعی صادر نشود.
5. اگر محدودیت مصرف/ابزار/زمان رخ داد، checkpoint موجود را حفظ کن و اجرای بعد از آخرین HEAD ادامه دهد. زمان reset را حدس نزن، retry سریع نامحدود انجام نده و عبور از محدودیت یا اجرای قطع‌نشده را وعده نده.
6. اگر فقط blocker نیازمند اقدام کاربر مانده، کار فنی بی‌اثر و mutation تکراری انجام نده. در گزارش آخر نیاز دقیق را بنویس و از کنترل مجاز automation برای توقف موقت استفاده کن؛ توقف توسعه نباید یادآوری شخصی کاربر را خودسرانه خاموش کند.

## معیار پایان و توقف

تکمیل تنها وقتی تأیید می‌شود که ماتریس تست، APIهای لازم، همه منوها/نقش‌ها، داده پایدار، سناریو کامل پذیرش تا تحویل، رگرسیون، امنیت، چاپ/موبایل و بازیابی شواهد واقعی داشته باشند؛ P0/P1 باز صفر و تست حیاتی blocked نباشد. خطر حذف اطلاعات، نشت دسترسی، تضاد قواعد یا نیاز به authority جدید = توقف و گزارش.

پس از تأیید واقعی تکمیل، پیشرفت را `verified_complete` کن، گزارش نهایی بده و فقط automation توسعه همین Site را با کنترل موجود pause کن. automation یادآوری شخصی جداست. اگر ابزار توقف موجود نیست، توقف خودکار را ادعا نکن و اطلاع بده.
